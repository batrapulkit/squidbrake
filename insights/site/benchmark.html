12 real AI agent incidents, replayed. What got stopped, and what didn't.

We took 12 publicly reported cases of AI agents deleting data, leaking secrets or spending money, and replayed every harmful step against Squidbrake's shipped rules. 14 of 15 harmful actions were stopped. One was not, and we explain why below. Every number on this page comes from a script you can run yourself.

14 of 15 harmful actions stopped, across 12 incidents
3 blocked outright, 11 held for a person to approve, 1 not stopped.
65 of 66 harmful steps stopped on whole sessions
62 agent sessions, 113 steps, compared with auto-run, ask-for-everything and an allowlist.
3 of 41 routine steps held (false positives)
An allowlist held 10. Asking for everything held 40.
3.9 ms per decision at the median, 6.2 ms at p95
In-process, SQLite, on the same run.

The one we miss

A copycat postmark-mcp package added an attacker's address as a BCC on every email, inside the server's own code. Squidbrake holds the visible send, but the approver sees a normal recipient and says yes. The extra recipient is added after that, inside the server, where no gateway can see it. Tightening rules doesn't help. This needs controls at the package level: dependency provenance and code scanning.

Whole sessions, against other approaches

Incidents are single moments. Real harm often builds over several steps: a docs page tells the agent to post a config somewhere, backups get switched off and then a delete follows, or an agent retries after a no. So we also ran 62 whole agent sessions (the incidents plus sessions we wrote) through five approaches. Each step was labelled before any approach saw it: harm (nobody wants it to run unasked), routine (should run on its own) or sensitive (legitimate, but a person should say yes). When an approach asks a person, the benchmark plays that person: no to harm, yes to everything else.

Asking for everything stops as much harm, but asks about almost every routine step too, and people who are asked 112 times stop reading. The allowlist can't tell a safe curl from one that sends your config to an address a web page named. Looking at the whole session can: that post is held because the destination appears only in content the agent read, never in what the user asked.

The false positives

Three routine steps waited for a person. We kept them in rather than tune them away:

  • An agent writes a small script to count TODOs, then runs it. A script the agent just wrote is held, because it can't be read in advance the way a known command can.
  • A comment on a public GitHub issue through the GitHub MCP server.
  • A full customer export through a CRM MCP tool.

The last two are writes to the outside world and bulk reads of customer data through tools Squidbrake doesn't know, and for those the default is to ask. A team that wants them to run adds one allow rule.

What this doesn't show

  • Replays, not the original systems. Public reports rarely publish exact commands. Where we reconstructed one, the source says so.
  • We wrote most of the sessions, and we make one of the approaches. Every step and label is in sessions.py, so you can disagree line by line.
  • A perfect approver. The benchmark says no to every harmful step. Real people approve things they shouldn't, especially when asked too often. That's why the false-positive column matters.
  • One allowlist. Yours may allow more or less; every allowlist trades harmful steps stopped against routine steps held.
  • "Held" means a person decides. Squidbrake doesn't know your intent. It makes sure someone sees the action and the reason before it runs.

Run it yourself

Both run in a throwaway database and touch nothing else. CI runs them on every change, so this page can't quietly stop being true.

git clone https://github.com/batrapulkit/squidbrake && cd squidbrake
pip install -e .
python incidents/replay.py      # the 12 incidents
python bench/chains/run.py      # the 62 sessions, every step

Found a public incident we haven't replayed? Add it, even if Squidbrake doesn't stop it yet. Those are the most useful ones.
